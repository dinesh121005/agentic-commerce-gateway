# ADR-008: External Integration Adapter Architecture

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, Integration Engineer, Backend Engineer
- **Date**: 2026-11-10
- **Technical Area**: External Integrations & Connectors

---

## 1. Context
Merchants store their authoritative product catalogs, inventory levels, and customer orders across existing e-commerce systems, primarily WooCommerce and Shopify. To become the merchant's operational brain, the platform must connect to these external systems, ingest catalog items, synchronize inventory changes, and receive order webhooks.

## 2. Problem
How should the platform structure external commerce and payment connectors so that third-party API changes, rate limits, network outages, and protocol differences do not leak into core commerce domain logic?

## 3. Decision
We decide to adopt the **Ports and Adapters (Hexagonal) Architecture** for all external integrations under `app/integrations/`:

1. **Explicit Connector Port Interfaces**:
   - The commerce domain defines abstract ports: `IStoreConnector` (catalog sync, stock push, webhook receiver).
   - Domain models (`Product`, `Order`, `InventoryDelta`) remain completely independent of WooCommerce or Shopify JSON schemas.

2. **Independently Replaceable Adapters**:
   - `WooCommerceConnector`: Implements `IStoreConnector` using WooCommerce REST API v3 and HMAC webhook validation (prioritized in P1.3).
   - `ShopifyConnector`: Implements `IStoreConnector` using Shopify GraphQL Admin API (future).
   - Third-party SDKs and client libraries are strictly confined to their adapter directories.

3. **Data Normalization Boundary**:
   - All external data structures are normalized into platform-native Pydantic models upon entry.
   - Float prices from WooCommerce (`"19.99"`) are immediately validated and converted to integer paise (`1999`) at the adapter boundary.

4. **Credential Isolation**:
   - Integration credentials (`consumer_key`, `consumer_secret`, webhook tokens) are stored in `integration_credentials` encrypted with AES-256-GCM.

## 4. Alternatives Considered
1. **Direct Coupling in Commerce Domain**:
   - *Pros*: Faster to prototype one connector.
   - *Cons*: Commerce service becomes littered with `if platform == "WOOCOMMERCE"` branches; breaks clean architecture; testing requires mocking external API responses throughout core services.
2. **Third-Party Integration Middleware (Zapier / Make / Rovo)**:
   - *Pros*: Low-code connectors.
   - *Cons*: Adds cost per operation; latency unsuitable for real-time inventory reservation; compromises merchant credential custody.

## 5. Consequences
- **Positive**: Adding a new commerce platform (e.g. Magento, Amazon SP-API) requires writing a new adapter without touching core catalog or inventory logic; mock connectors allow 100% offline integration testing; failures in external APIs are gracefully isolated.
- **Negative**: Requires writing explicit bidirectional data mappers for each external platform.
- **Neutral**: Webhook endpoints must be versioned and routed dynamically based on store connection ID.

## 6. Security Implications
- External webhooks must verify signatures (e.g. `X-WC-Webhook-Signature`) using the merchant's stored webhook secret before dispatching payloads.
- Outbound requests to external merchant APIs enforce timeouts (10s) and retry backoff to prevent socket exhaustion.

## 7. Migration Implications
- Initial connector will be WooCommerce in P1.3; the existing static catalog seed (`app/catalog/data.py`) is retained as a local fallback store connector for offline testing.

## 8. Open Questions
- Should catalog sync be full mirror or delta-only? *Verdict*: Initial full sync upon store connection, followed by real-time webhook deltas and periodic reconciliation.
