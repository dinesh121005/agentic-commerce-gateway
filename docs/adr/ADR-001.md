# ADR-001: Adoption of Multi-Tenant Modular Monolith Architecture

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, System Architect, Backend Engineer
- **Date**: 2026-11-10
- **Technical Area**: System Architecture & Topology

---

## 1. Context
The existing Agentic Commerce Gateway is implemented as a single-process FastAPI application serving REST endpoints, MCP tools, and static admin interfaces. The business vision requires evolving the gateway into a multi-tenant Agentic Commerce Platform supporting multiple merchants, stores, employees, and AI workers. As architectures scale, organizations frequently debate decomposing applications into independent microservices or retaining a monolithic codebase.

## 2. Problem
How should the platform structure its codebase and runtime topology to support multi-tenancy, cross-domain coordination (commerce, payments, workforce, governance), and high engineering velocity without incurring excessive operational overhead, network serialization latency, or complex distributed transactions?

## 3. Decision
We decide to adopt a **Multi-Tenant Modular Monolith** architecture within the existing Python 3.12 / FastAPI codebase.
- Modules (`core`, `merchant`, `store`, `workforce`, `commerce`, `payments`, `governance`, `integrations`, `api`) remain strictly partitioned with explicit public service interfaces.
- Inter-module communication occurs via in-process typed Python method calls and in-memory domain events, rather than network RPC/HTTP.
- The entire system deploys as a unified runtime process, with dedicated background workers sharing the codebase.

## 4. Alternatives Considered
1. **Microservices Architecture**:
   - *Pros*: Independent deployment cycles, per-service technology selection, isolated blast radiuses.
   - *Cons*: Distributed transactions (Sagas/2PC) required for order-inventory-payment sync; complex network failure modes; significant operational overhead (Kubernetes, service meshes, distributed tracing); slower development iteration for a startup/growth stage.
2. **Traditional Monolith (Unstructured)**:
   - *Pros*: Minimal initial setup.
   - *Cons*: Spaghetiffication of domain logic; leaky abstractions; tight coupling between payment rails and AI tools; high regression risks during concurrent feature development.

## 5. Consequences
- **Positive**: Single repository; zero network latency between commerce and governance checks; unified database transactions across co-located tables; simplified debugging and test execution (local pytest); single CI/CD pipeline.
- **Negative**: Risk of developers bypassing module boundaries if architectural discipline is not enforced; entire application shares process CPU/memory resources.
- **Neutral**: Boundaries are designed cleanly so that if a domain (e.g. `workforce` or `payments`) requires horizontal scaling later, it can be extracted into an independent microservice with minimal interface changes.

## 6. Security Implications
- Strong module encapsulation prevents accidental leakage of payment secrets or audit hash keys to the AI workforce layer.
- Thread/async safety must be maintained in global state; request-scoped tenant context must not bleed across coroutines.

## 7. Migration Implications
- Preserves the existing `app/` folder structure initially; facilitates strangler migration without rewriting network plumbing.
- Existing tests run directly in-process without mocking network services.

## 8. Open Questions
- None. Consensus reached on modular monolith.
