# ADR-007: Separation of AI Execution and Deterministic Business Services

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, AI Systems Architect, Security Engineer
- **Date**: 2026-11-10
- **Technical Area**: AI Safety & Governance

---

## 1. Context
The platform provisions a multi-agent AI workforce (Sales, Customer Support, Inventory, Growth, Order Operations, Finance) to assist merchants in operating their businesses. In modern LLM applications, there is an acute danger of allowing probabilistic AI models to directly mutate databases, calculate prices, or issue payments.

## 2. Problem
How do we empower autonomous AI workers to perform complex, multi-step business operations while guaranteeing that probabilistic hallucinations, prompt injections, or model drift cannot corrupt financial ledgers, oversell stock, or execute unauthorized transactions?

## 3. Decision
We decide to enforce a strict **Architectural Separation between Probabilistic AI Reasoning and Deterministic Business Services**:

1. **AI Models Are Never the Source of Truth**:
   - LLMs are treated as untrusted reasoning and natural-language processing engines.
   - Financial totals, pricing rules, inventory availability, tax calculations, and payment state machines are computed and enforced **exclusively by deterministic Python domain services**.

2. **Permission-Controlled Tool Sandbox**:
   - AI agents can only interact with the outside world through typed domain tools (e.g. `search_products`, `reserve_stock`, `create_quote`).
   - Every tool execution strictly runs within the authenticated merchant's `TenantContext` and checks the agent instance's `agent_permissions`.

3. **Mandatory Human-in-the-Loop Escalation Gates**:
   - Any agent action that exceeds a pre-configured financial threshold (e.g. order value $\ge$ ₹500, or custom merchant threshold), applies an unusual discount, or alters inventory outside safe variance requires explicit human approval via `purchase_approvals`.
   - The tool suspends task execution into `AWAITING_APPROVAL` status until a merchant employee signs or confirms the action.

## 4. Alternatives Considered
1. **Direct Agent Database Mutations (SQL Agent)**:
   - *Pros*: Extreme flexibility; agents can execute arbitrary SQL queries.
   - *Cons*: Catastrophic security and integrity risk; prompt injection allows an attacker to drop tables, alter prices to zero, or read other tenants' data. Absolutely rejected.
2. **Post-Action Async Audit Only (No Pre-Execution Gating)**:
   - *Pros*: Faster autonomous execution without waiting for human confirmation.
   - *Cons*: Money lost and inventory oversold before human notice; irreversible financial damage.

## 5. Consequences
- **Positive**: Complete defense against prompt injection compromising core commerce data; business rules remain transparent, deterministic, and unit-testable; compliance with financial auditing standards.
- **Negative**: Certain complex buyer inquiries require human approval latency before completion; requires implementing a human escalation task queue in the UI.
- **Neutral**: Agents can still perform read-only queries and bounded proposals instantaneously.

## 6. Security Implications
- Preserves the 7 Inviolable LLM Security Principles established in P0.
- AI prompt outputs are sanitized and validated against Pydantic schemas before ingestion into domain services.

## 7. Migration Implications
- Wraps the existing `app/merchant_agent/` Gemini prototype into the new workforce tool framework.
- Upgrades `app/agent/service.py` to route through the unified governance policy engine.

## 8. Open Questions
- What default timeout should apply to pending human approvals before automatic expiration? *Verdict*: 24 hours default, configurable per merchant.
