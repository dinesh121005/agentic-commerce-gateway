# ADR-005: Strangler Migration Strategy for Gateway Transformation

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, Software Architect, DevOps Engineer
- **Date**: 2026-11-10
- **Technical Area**: Migration & Delivery Strategy

---

## 1. Context
The repository houses a fully functioning, heavily tested Agentic Commerce Gateway with 279 passing automated tests. Existing capabilities include Buyer AI purchase orchestration, dual-transport MCP servers, Ed25519 mandate verification, Razorpay test rails, and SHA-256 audit chaining. Transforming this system into a multi-tenant platform carries high risk of regression if attempted via a "big-bang" codebase rewrite.

## 2. Problem
How do we progressively introduce multi-tenancy, merchant identity, WooCommerce synchronization, AI workforce management, and Paytm orchestration without breaking existing gateway functionality or disrupting current test suites?

## 3. Decision
We decide to execute a **Strangler Fig Migration**:
1. **Preserve Baseline Entrypoints**: All existing routes (`/catalog`, `/agent`, `/audit`, `/payment`, `/mcp`, `/admin`) remain functional throughout all P1 milestones.
2. **Side-by-Side Coexistence**: New multi-tenant domain packages (`app/core/`, `app/merchant/`, `app/store/`, `app/workforce/`, `app/commerce/`, `app/payments/`, `app/governance/`, `app/integrations/`) are introduced alongside legacy modules.
3. **Façade Re-routing**: Legacy endpoints and functions will be updated to act as thin façades that route requests into the new multi-tenant domain services using a default demo tenant (`'MERCH_DEFAULT'`).
4. **No Destructive Actions**: No legacy tables, columns, or routes will be removed until equivalent multi-tenant functionality is deployed, verified, and backed by automated regression tests.

## 4. Alternatives Considered
1. **Big-Bang Architecture Rewrite**:
   - *Pros*: Clean slate; no legacy façade code.
   - *Cons*: High regression probability; breaks existing 279 tests; months of un-deployable branch drift; impossible to verify incremental correctness.
2. **Branch-and-Merge**:
   - *Pros*: Work isolated on feature branches.
   - *Cons*: Painful merge conflicts; delays feedback on architectural validity.

## 5. Consequences
- **Positive**: Zero downtime; existing tests remain green across all intermediate commits; incremental verification of each domain; low deployment risk.
- **Negative**: Temporary duplication of logic between legacy façades and new domain services; codebase is slightly larger during the transition period.
- **Neutral**: Requires clear deprecation warnings on legacy routes to signal future retirement.

## 6. Security Implications
- Legacy routes continue to enforce their proven P0 security controls (VULN-01 to VULN-08 mitigations) without regression.
- New routes enforce multi-tenant authentication from day one.

## 7. Migration Implications
- Requires a designated seed merchant organization (`MERCH_DEFAULT`) to adopt orphaned legacy records (catalog items, audit logs, demo mandates).
- Database migrations must be purely additive (expand phase) during early milestones, deferring column drops (contract phase) to future major versions.

## 8. Open Questions
- When should legacy single-tenant endpoints be formally retired? *Verdict*: Maintained through P1.x; scheduled for formal deprecation review in P2.0.
