## 1. Context
In a multi-tenant commerce platform, a breach of tenant isolation (e.g. one merchant seeing another merchant's sales, inventory, or customer orders) represents a critical failure. The system must guarantee complete data and operational segregation between merchants across API requests, background jobs, and database queries.

## 2. Problem
How do we enforce tenant isolation robustly across the application and database layers while preventing developer oversight (e.g. omitting a `WHERE merchant_id = ...` clause) from creating BOLA/IDOR vulnerabilities?

## 3. Decision
We decide to adopt a **Defense-in-Depth Tenant Isolation Strategy** combining three synchronized enforcement mechanisms:

1. **Authoritative Server Context Resolution**:
   - `merchant_id` is extracted strictly from cryptographically verified JWT claims (`claims["merchant_id"]`) in `TenantContextMiddleware`.
   - The resolved context is stored in Python's `contextvars.ContextVar`, safe across async task boundaries.
   - Any client-submitted `merchant_id` in request bodies or query parameters is strictly forbidden as an authorization signal.

2. **Application-Layer Tenant-Scoped Data Access**:
   - Every domain repository and query builder requires `tenant_context.merchant_id` to construct SQL queries.
   - Compound primary and unique constraints include `merchant_id` (e.g. `PRIMARY KEY (merchant_id, id)`).

3. **PostgreSQL Row-Level Security (RLS) as Defense in Depth**:
   - In production PostgreSQL, database connections set a transaction-scoped local variable inside an explicit transaction block: `SET LOCAL app.current_merchant_id = '<merchant_id>'`. Using `SET LOCAL` guarantees that the variable automatically clears when the transaction commits or rolls back, completely eliminating connection pool session bleed.
   - Connection pool checkout/checkin hooks execute `DISCARD TEMP` / `RESET ALL` upon return to the pool as a failsafe.
   - The application connects via a dedicated non-superuser database role (`app_user`) with `NOBYPASSRLS` privileges.
   - All tenant-owned tables enforce `ALTER TABLE ... FORCE ROW LEVEL SECURITY;`, ensuring that RLS policies are applied even if queries run under the table owner account.
   - Background jobs and outbox workers execute within an explicit transaction that sets `SET LOCAL app.current_merchant_id = job.merchant_id` before processing.

## 4. Alternatives Considered
1. **Application-Only Filtering (No RLS)**:
   - *Pros*: Simple setup; works identically on SQLite without special session configuration.
   - *Cons*: High human-error vulnerability; one developer missing a WHERE filter leads to catastrophic data leakage.
2. **Database-per-Tenant**:
   - *Pros*: Absolute physical isolation.
   - *Cons*: Immense operational complexity, database migration nightmare across hundreds of schemas/databases, resource overhead on cloud hosting.
3. **Schema-per-Tenant**:
   - *Pros*: Strong logical isolation.
   - *Cons*: Complex connection pooling; high migration latency across dynamic schemas; foreign keys cannot easily reference global system catalogs.

## 5. Consequences
- **Positive**: Absolute mathematical guarantee against cross-tenant data leaks; RLS catches accidental ORM or raw SQL leaks; transparent to upper business logic.
- **Negative**: Test harness on local SQLite cannot execute PostgreSQL RLS policies; test suite must validate application-level scoping explicitly while running dedicated dialect tests for RLS.
- **Neutral**: Connection pooling requires resetting `app.current_merchant_id` upon session release to prevent session contamination.

## 6. Security Implications
- Neutralizes OWASP Top 10 BOLA (Broken Object-Level Authorization) at the database layer.
- Background worker jobs must explicitly bind the tenant context when dequeuing an outbox task.

## 7. Migration Implications
- Requires enabling RLS on tables in migration scripts: `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`.
- Superuser database connections bypass RLS by default; runtime application connections must connect as a non-superuser role (`app_user`).

## 8. Open Questions
- None. Defense-in-depth model accepted.
