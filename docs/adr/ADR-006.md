# ADR-006: Provider-Neutral Payment Orchestration & Paytm Integration

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, Payment Systems Architect, Backend Engineer
- **Date**: 2026-11-10
- **Technical Area**: Payments & Financial Rails

---

## 1. Context
The platform direction designates **Paytm as the intended primary payment infrastructure**, while preserving existing Razorpay test rails. In the baseline code, payment handling is tightly coupled to Razorpay SDK calls inside `app/payment/service.py` and `app/payment/router.py`. Directly replacing Razorpay with Paytm would create vendor lock-in and break existing test suites.

## 2. Problem
How do we integrate Paytm as the primary payment processor while cleanly abstracting payment operations, preserving Razorpay fallback/test support, and enforcing strict financial safety invariants across multiple tenants?

## 3. Decision
We decide to introduce a **Provider-Neutral Payment Orchestrator** backed by an explicit adapter interface (`IPaymentProvider`):
1. **Domain Abstraction**: The core commerce layer interacts solely with platform-native payment constructs: `PaymentIntent`, `PaymentTransaction`, and `RefundIntent`.
2. **Pluggable Adapters**:
   - `PaytmPaymentAdapter`: Primary production adapter using Paytm All-in-One Payment Gateway APIs, dynamic UPI QR, and Paytm Checksum signature verification.
   - `RazorpayPaymentAdapter`: Preserved adapter wrapping existing Razorpay Orders, Payment Links, and HMAC verification.
3. **Internal Payment Router**: A dedicated routing service evaluates merchant preference, transaction amount, and rail availability to select the target provider adapter.
4. **Paytm Scoping Realism**: Paytm is integrated as an acquiring payment gateway. The platform **does not assume** Paytm provides multi-gateway meta-routing across competing processors; meta-routing is handled internally by the platform orchestrator.
5. **Integer-Paise Financial Representation**: Positive 64-bit integer paise are strictly enforced across all payment interfaces.

## 4. Alternatives Considered
1. **Direct Paytm Replacement**:
   - *Pros*: Faster single-provider implementation.
   - *Cons*: Deletes working Razorpay rails; breaks 26 payment tests; locks platform to Paytm API quirks.
2. **Third-Party Payment Orchestration SaaS (Juspay / Hyperswitch)**:
   - *Pros*: Off-the-shelf routing.
   - *Cons*: Additional recurring SaaS cost; external dependency for core IP; complex local testing.

## 5. Consequences
- **Positive**: Clean separation of business logic from gateway SDKs; independent testability via mock adapters; easy addition of future rails (PhonePe, Stripe); zero downtime during provider outages.
- **Negative**: Requires writing adapter shims and mapping provider-specific webhook events to a normalized platform status enum.
- **Neutral**: Both Paytm and Razorpay adapters share the same database idempotency and deduplication tables (`processed_webhook_events`).

## 6. Security Implications
- Payment credentials (`paytm_merchant_key`, `razorpay_key_secret`) are encrypted at rest with AES-256-GCM.
- Raw webhook payloads must be preserved byte-for-byte to enable reliable cryptographic signature re-verification.
- AI agents cannot access provider adapters or credentials under any circumstance.

## 7. Migration Implications
- Existing `/payment/verify` and `/payment/create-order` endpoints are wrapped to invoke the orchestrator with provider forced to `RAZORPAY`.
- New multi-tenant checkout routes route to Paytm by default when merchant credentials are configured.

## 8. Open Questions
- What Paytm merchant onboarding model will be supported (Direct Merchant MID vs. Marketplace Aggregator)? *Verdict*: Direct Merchant MID first (P1.4), aggregator mode deferred.
