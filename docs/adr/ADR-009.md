# ADR-009: Background Processing & Event Delivery Strategy

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, DevOps Engineer, Backend Engineer
- **Date**: 2026-11-10
- **Technical Area**: Asynchronous Infrastructure & Event Delivery

---

## 1. Context
The platform requires asynchronous background processing for several operations: external store catalog synchronization (WooCommerce), periodic payment reconciliation, retry polling for ambiguous payment timeouts, webhook delivery, and scheduled AI workforce audits. The current baseline repository has **zero background job queue infrastructure**; all operations execute synchronously inside the FastAPI request-response loop.

## 2. Problem
How should asynchronous processing and reliable event delivery be implemented without prematurely introducing complex distributed message brokers (Kafka, RabbitMQ, Celery/Redis) that increase operational overhead and infrastructure costs?

## 3. Decision
We decide to implement a **Database-Backed Transactional Outbox Pattern with an In-Process Async Worker**:

1. **Transactional Outbox Table (`event_outbox`)**:
   - Outbound tasks and events are inserted into the authoritative PostgreSQL database as part of the same ACID transaction that updates business state.
   - Example: When an order is placed, both the order record and the `order.created` outbox event are committed atomically in one database transaction. This eliminates the dual-write problem.

2. **Durable Worker Loop (`app/integrations/outbox.py`)**:
   - A lightweight, durable background worker running inside the modular monolith process periodically polls the outbox using PostgreSQL `FOR UPDATE SKIP LOCKED`.
   - `SELECT * FROM event_outbox WHERE status = 'PENDING' ORDER BY scheduled_at ASC LIMIT 10 FOR UPDATE SKIP LOCKED;`
   - Guarantees exactly-once dispatch without lock contention across multiple application replicas.

3. **Redis Deferral**:
   - Redis is not required for P1. Redis is justified only when job throughput exceeds hundreds of tasks per second or sub-second pub/sub is required. PostgreSQL handles thousands of outbox events per second with zero extra operational infrastructure.

4. **Tenant Context Preservation**:
   - Every outbox record includes `merchant_id`. When the worker thread picks up a task, it explicitly binds `TenantContext(merchant_id)` into the execution context before invoking domain handlers.

## 4. Alternatives Considered
1. **Celery + Redis**:
   - *Pros*: Popular Python task queue.
   - *Cons*: Introduces Redis operational requirement; dual-write vulnerability (if database commits but Redis enqueue fails, events are lost); steep configuration curve.
2. **Kafka / AWS SQS**:
   - *Pros*: Massive horizontal scale.
   - *Cons*: Severe architectural overkill for P1; expensive; high local developer friction; complex partition management.
3. **FastAPI `BackgroundTasks`**:
   - *Pros*: Built-in; zero dependencies.
   - *Cons*: In-memory only; if the server restarts or crashes, all queued tasks are permanently lost. Unacceptable for financial or store sync tasks.

## 5. Consequences
- **Positive**: 100% reliable event delivery (at-least-once guarantee); atomic commits with domain state; zero new infrastructure dependencies beyond PostgreSQL; works seamlessly in both single-instance and multi-replica environments.
- **Negative**: Polling adds slight database read load; requires maintaining task state transitions (`PENDING`, `PROCESSING`, `COMPLETED`, `FAILED`).
- **Neutral**: When scale demands, the outbox worker can be extracted to a standalone worker container without changing domain code.

## 6. Security Implications
- Background jobs cannot execute with a default or global admin identity; they must strictly inherit the `merchant_id` of the outbox payload.
- Failed tasks log structured error traces without exposing encrypted credentials in log storage.

## 7. Migration Implications
- Initial implementation created in `app/integrations/outbox.py` in P1.3 to support WooCommerce synchronization.

## 8. Open Questions
- Maximum retry count before dead-lettering? *Verdict*: 5 retries with exponential backoff ($2^n \times 30$ seconds), then status transitions to `DEAD_LETTER` with admin alert.
