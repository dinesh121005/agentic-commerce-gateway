## 2. Updated Database Transaction Lifecycle

The diagram below illustrates the exact transaction lifecycle from HTTP request ingestion to database execution and connection release:

```mermaid
sequenceDiagram
    autonumber
    actor Client as Merchant Client / Agent
    participant Middleware as Auth Middleware (FastAPI)
    participant Context as TenantContext (contextvars)
    participant Service as Domain Service Layer
    participant DBPool as Database Access Layer (app/db.py)
    participant PG as PostgreSQL 16 (app_user)

    Client->>Middleware: HTTP Request + Bearer JWT
    Middleware->>Middleware: Verify JWT signature & token_version
    Middleware->>Context: set_current_tenant_context(ctx)
    Note over Context: TenantContext(user_id, merchant_id, role) bound to async task

    Middleware->>Service: Dispatch Request to Router / Handler
    Service->>DBPool: with get_db_connection() as conn
    DBPool->>PG: Checkout connection (autocommit=False)
    Note over PG: Active Transaction Begins Automatically

    DBPool->>Context: get_current_tenant_context()
    alt Tenant Context Present
        DBPool->>PG: SET LOCAL app.current_merchant_id = 'MERCH_...';
        DBPool->>PG: SET LOCAL app.current_user_id = 'USER_...';
    else Missing / Public Context
        DBPool->>PG: SET LOCAL app.current_merchant_id = '';
        Note over PG: Fails Closed on Tenant-Scoped Tables
    end

    Service->>PG: cursor.execute("SELECT * FROM catalog_products;")
    Note over PG: RLS Evaluates Predicate: merchant_id = current_setting('app.current_merchant_id')
    PG-->>Service: Return Tenant-Scoped Rows Only

    Service->>DBPool: conn.commit() (or exception -> conn.rollback())
    DBPool->>PG: COMMIT / ROLLBACK
    Note over PG: PostgreSQL Automatically Erases All SET LOCAL Parameters!
    
    DBPool->>PG: Connection closed / returned to pool
    Note over PG: Zero Residual Tenant Context in Connection Pool
    Service-->>Client: HTTP 200 Response
```

### Key Transaction Lifecycle Properties
1. **Transaction Boundary Ownership:** Transaction boundaries are managed at the context manager level (`with get_db_connection() as conn:`). Every write operation explicitly calls `conn.commit()`; unhandled exceptions trigger `conn.rollback()`.
2. **Atomic Context Lifecycle:** `SET LOCAL` is bound to the exact transaction executing the domain query. When `COMMIT` or `ROLLBACK` executes, PostgreSQL's transaction manager wipes the GUC parameter automatically.
3. **Connection Pooling Safety:** Physical connections reused across multiple HTTP requests cannot leak tenant context because no session-level state persists past the transaction boundary.

## 4. Authentication Bootstrap Architecture

### The Bootstrap Challenge
Before a merchant employee logs in, lists their organizations, switches between tenants, or accepts an invitation, **no active merchant context exists**. If tables like `merchant_memberships` and `merchant_invitations` enforce single-tenant RLS (`merchant_id = app.current_merchant_id`), these queries fail closed and block authentication.

### The Safe Bootstrap Solution
Rather than exempting these tables from RLS, we implement **dual-predicate authorization policies**:

1. **`merchant_memberships` (User Identity vs. Org Dimension):**
   ```sql
   CREATE POLICY tenant_isolation_memberships ON merchant_memberships
       AS PERMISSIVE FOR ALL
       USING (
           (merchant_id = NULLIF(current_setting('app.current_merchant_id', true), '') AND merchant_id IS NOT NULL)
           OR (user_id = NULLIF(current_setting('app.current_user_id', true), '') AND user_id IS NOT NULL)
       )
       WITH CHECK (
           merchant_id = NULLIF(current_setting('app.current_merchant_id', true), '') AND merchant_id IS NOT NULL
       );
   ```
   - **Login & Org Switching:** The authenticated user sets `app.current_user_id = '<user_id>'` and can only see memberships belonging to their own identity.
   - **Org Management:** An active merchant admin sets `app.current_merchant_id = '<merchant_id>'` and can manage memberships within their organization.
   - **Cross-Tenant Barrier:** A user cannot inspect memberships of other users in other organizations.
   - **Write Safety:** Creating/updating memberships strictly requires active `app.current_merchant_id`.

2. **`merchant_invitations` (Cryptographic Token Match):**
   ```sql
   CREATE POLICY tenant_isolation_invitations ON merchant_invitations
       AS PERMISSIVE FOR ALL
       USING (
           (merchant_id = NULLIF(current_setting('app.current_merchant_id', true), '') AND merchant_id IS NOT NULL)
           OR (token_hash = NULLIF(current_setting('app.current_invitation_token_hash', true), '') AND token_hash IS NOT NULL)
       )
       WITH CHECK (
           merchant_id = NULLIF(current_setting('app.current_merchant_id', true), '') AND merchant_id IS NOT NULL
       );
   ```
   - Unauthenticated invitation acceptance is granted access **strictly to the single row matching the high-entropy SHA-256 token hash**.
   - Mass scanning or enumeration of pending invitations is completely blocked.

## 5. Audit Event Architecture & Global Ledger Invariants

### Ownership Derivation Precedence
To prevent malicious callers from injecting arbitrary `merchant_id` values into event payloads, `AuditStore._append_event()` derives ownership with strict server-side precedence:
1. **Authoritative `TenantContext`:** Server-side context established by JWT verification overrides any caller-supplied payload.
2. **Trusted Transaction Association:** For async callbacks and compensations without request context, `merchant_id` is inherited from the verified `audit_records` row.
3. **System Events:** Unassociated platform events explicitly store `merchant_id = NULL`.

### Cryptographic Hash-Chain Invariant
The event hash is computed as:
$$\text{SHA-256}(\text{prev\_hash} \parallel \text{event\_id} \parallel \text{transaction\_id} \parallel \text{event\_type} \parallel \text{timestamp} \parallel \text{payload\_json})$$
The database column `merchant_id` is a relational index/filtering attribute and is **not an input to the cryptographic hash function**. Historical hashes and live chain verification (`verify_integrity()`) remain 100% valid and mathematically continuous (`VERIFIED_IMMUTABLE`).

## 6. Threat Model: Custom GUC Parameters & System-Event Access

### The Threat
Custom PostgreSQL configuration settings (e.g. `SET LOCAL app.current_merchant_id = '...'`) are modifiable by the database role `app_user` via standard SQL. 
Therefore:
> **Security Invariant:** RLS driven by custom GUCs is defense-in-depth against application bugs (omitted `WHERE` clauses). It does **not** constitute an unforgeable boundary against an attacker with arbitrary SQL execution rights.

### System-Event Access Hardening
A naive policy allowing `OR current_setting('app.is_system_context', true) = 'true'` is insecure because any session running under `app_user` could execute `SET LOCAL app.is_system_context = 'true'`.

**The Defense-in-Depth Solution:**
1. **On `audit_events`:** The policy for `app_user` strictly enforces:
   ```sql
   merchant_id = NULLIF(current_setting('app.current_merchant_id', true), '') AND merchant_id IS NOT NULL
   ```
   Under this policy, merchant runtime sessions **have no SQL path to access rows where `merchant_id IS NULL`**.
2. **Platform & Maintenance Operations:** Full-ledger integrity audits (`verify_integrity()`) and system event administration run as dedicated platform services or under the schema owner (`gateway_admin`), isolating system-level auditing from merchant runtime boundaries.

## 8. List of Unresolved Risks and Proposed Mitigations

| Risk | Severity | Technical Description | Mitigation / Architectural Decision |
|---|---|---|---|
| **1. Unenforced RLS in SQLite** | Medium | Local unit tests default to SQLite, which lacks native RLS policies. Bugs in SQL generation could pass SQLite and fail on PostgreSQL. | The 19 dedicated PostgreSQL tests run directly against PostgreSQL 16. Future CI must run the full test suite against PostgreSQL in containerized pipelines. |
| **2. Arbitrary SQL Attack Surface** | High | An attacker who achieves raw SQL injection through `app_user` could execute `SET LOCAL app.current_merchant_id = 'TARGET'`. | Strictly enforce parameterized queries (`%s`), validate all inputs via Pydantic schemas, and never expose direct SQL capabilities to AI agents or clients. |
| **3. Cross-Tenant AI Tool Execution** | High | An AI agent operating on behalf of Merchant A might call a tool specifying Merchant B's product or transaction ID. | Domain tools derive the target tenant strictly from the server-side `TenantContext`, ignoring client/agent-supplied merchant IDs. |
| **4. Performance Overhead of `SET LOCAL`** | Low | Executing `SET LOCAL` on every connection checkout adds ~0.1ms per transaction. | Microbenchmark confirms negligible latency impact relative to database query execution times. Compound indexes ensure zero table scans. |
