# ADR-004: PostgreSQL as the Authoritative Transactional Database

- **Status**: PROPOSED
- **Deciders**: Lead Orchestrator, Database Architect, Backend Engineer
- **Date**: 2026-11-10
- **Technical Area**: Persistence & Data Integrity

---

## 1. Context
The existing baseline operates with a dual database abstraction (`app/db.py`) supporting local SQLite (`gateway.db`) and PostgreSQL (`psycopg2-binary`) via runtime string-replacement wrappers. SQLite lacks robust row-level concurrency locking (`SELECT ... FOR UPDATE`), fine-grained ACID isolation levels under concurrent writes, native JSONB querying, Row-Level Security, and connection pooling.

## 2. Problem
Which database engine should serve as the authoritative production transactional database for the multi-tenant platform, and how should local development and testing be managed?

## 3. Decision
We decide that **PostgreSQL 16+ is the sole authoritative transactional database for all production deployments**:
1. All schema DDL, constraints, foreign keys, row locks, RLS policies, and performance indexes are designed natively for PostgreSQL.
2. For developer ergonomics and fast, dependency-free local test execution, the existing SQLite compatibility layer in `app/core/db.py` is maintained for unit test suites (`pytest`), with dialect tests validating PostgreSQL syntax in CI.
3. Production runtime connections will adopt robust connection pooling (`psycopg_pool` or `SQLAlchemy / AsyncPG`) to replace the current unpooled `psycopg2.connect` pattern.

## 4. Alternatives Considered
1. **SQLite in Production**:
   - *Pros*: Zero external infrastructure.
   - *Cons*: Database-level locking (`SQLITE_BUSY`), single concurrent writer bottleneck, risk of lock timeouts during concurrent checkout spikes, lack of RLS. Unsuitable for multi-tenant SaaS.
2. **Document Database (MongoDB / DynamoDB)**:
   - *Pros*: Flexible document schemas for catalog attributes.
   - *Cons*: Weak cross-document ACID transactions; high complexity for inventory reservations and financial ledger consistency; no native relational foreign key integrity across merchants, stores, and orders.

## 5. Consequences
- **Positive**: Strict ACID transaction guarantees; atomic row-level locking (`SELECT ... FOR UPDATE`) for reservations and inventory decrement; native JSONB support for agent task payloads and role permissions; full RLS support for tenant isolation.
- **Negative**: Requires hosted PostgreSQL instance (Render, Supabase, AWS RDS) for staging and production environments.
- **Neutral**: SQLite wrapper maintained purely as a lightweight test-runner fixture.

## 6. Security Implications
- Strong transaction isolation (`READ COMMITTED` or `REPEATABLE READ`) prevents phantom reads and race conditions during payment webhook settlements and inventory holds.
- Encrypted connections (SSL `require`) mandated in production.

## 7. Migration Implications
- Move from manual DDL queries inside `_init_db()` to versioned Alembic database migrations.
- Expand-and-contract migration strategy ensures zero-downtime database upgrades.

## 8. Open Questions
- Should migration to SQLAlchemy 2.0 / Alembic occur in P1.1 or P1.2? *Verdict*: Introduce Alembic in P1.1 alongside the merchant table introduction.
